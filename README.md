# M&A Comparable Company & Valuation Analyzer

An end-to-end investment-banking-style comps and valuation tool: pick a target
company, get its financial profile, a ranked comparable-company set (cosine
similarity on scaled financial features), precedent M&A transaction
multiples, and a blended Low/Base/High enterprise-value range — all backed by
deterministic, auditable calculations.

Built for **₹0 / $0**: no cloud, no paid APIs, no paid hosting.

> This project is for educational and research purposes and does not
> constitute financial or investment advice.

## 1. Architecture

```
CSV (data/raw/)
        │
        ▼
Python + Pandas ETL  (ingest → validate → clean → transform)
        │
        ▼
DuckDB  (data/processed/mna.duckdb — embedded, zero setup)
        │
        ▼
Financial Analytics (src/analytics)      — pure Python, EV & ratios
ML Comps Engine     (src/ml)             — StandardScaler + cosine similarity
Valuation Engine    (src/valuation)      — trading comps + precedent txns
        │
        ▼
FastAPI backend (backend/)  ──REST/JSON──►  React + Vite frontend (frontend/)
```

The ML layer only *ranks similarity* — it never touches a dollar figure.
Every number on the Valuation tab is traceable back to raw data → a
calculated multiple → an applied multiple → an estimate, and is labeled as
such.

## 4. Dataset

- **`data/raw/companies.csv`** — 20 publicly traded software/tech companies
  with financials sourced from public 10-K filings and market data
  (approximate, latest available fiscal year at time of writing). Fields:
  revenue, revenue growth, EBITDA, net income, debt, cash, shares
  outstanding, share price.
- **`data/raw/transactions.csv`** — 25 real, publicly disclosed M&A deals in
  enterprise software (2018–2024), with deal value and EV/Revenue,
  EV/EBITDA multiples as reported at announcement.

**Limitations (be upfront about these — they're also good interview
material):** both datasets are static snapshots, not live-refreshed; the
universe is small (20 companies / 25 deals) so percentile statistics have
wide confidence bands; some listed companies (e.g. Splunk, VMware) have
since been acquired and are included as historical reference points, not
current public comps; deal multiples embed an unquantified control premium
relative to trading comps.

## 5. Financial & ML Methodology

**Ratios & EV** (`src/analytics/financials.py`): plain arithmetic —
`EV = Market Cap + Total Debt − Cash`, `EV/Revenue`, `EV/EBITDA`, `P/E`,
`Debt/EBITDA`, EBITDA margin. Ratios return `None` (displayed as "NM") when
the denominator is zero or negative — e.g. P/E for a loss-making company —
rather than producing a misleading number.

**Comparable companies** (`src/ml/comps.py`): features (revenue, revenue
growth, EBITDA margin, market cap, EV, Debt/EBITDA) are standardized
(`StandardScaler`) so no single metric dominates by magnitude alone, then
ranked by cosine similarity to the target. This is deliberately unsupervised
— there's no ground-truth "correct comp set" to train a classifier against,
so a similarity ranking is the honest, explainable choice.

**Valuation** (`src/valuation/engine.py`): trading comps apply the peer
group's 25th/median/75th-percentile EV/Revenue and EV/EBITDA to the target's
own revenue/EBITDA; precedent transactions do the same using historical deal
multiples for the target's industry. The two methods are blended into a
single Low/Base/High. Every output carries a disclaimer.

## 6. Installation & Setup

**Prerequisites:** Python 3.11+, Node.js 18+, npm.

```bash
# 1. Clone / unzip the project, then from the project root:
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

# 2. Load the data into DuckDB (creates data/processed/mna.duckdb)
python -m src.ingestion.load_data
# Expected output: ETL complete: {'companies_loaded': 20, 'transactions_loaded': 25}

# 3. Run the test suite (optional but recommended)
pytest tests/ -v
# Expected: 19 passed

# 4. Install frontend dependencies
cd frontend
npm install
cd ..
```

## 7. Running the App

You need **two terminals** — the backend and frontend run as separate
processes.

**Terminal 1 — backend (from the project root):**
```bash
uvicorn backend.main:app --reload --port 8000
```
Visit `http://127.0.0.1:8000/docs` to see interactive API docs (FastAPI
auto-generates this — try `GET /api/valuation/C001` there directly).

**Terminal 2 — frontend:**
```bash
cd frontend
npm run dev
```
Open the URL it prints (typically `http://127.0.0.1:5173`). Select a company
in the sidebar and move through the Overview / Comparables / Transactions /
Valuation tabs.

**Company IDs** run `C001`–`C020` (see `data/raw/companies.csv`); e.g. `C001`
is Salesforce, `C002` is Oracle.

### Production build (optional)

```bash
cd frontend
npm run build      # outputs static files to frontend/dist/
npm run preview    # serve the production build locally to sanity-check it
```

## 8. Re-running the ETL

If you edit `data/raw/companies.csv` or `transactions.csv`, re-run:
```bash
python -m src.ingestion.load_data
```
This drops and rebuilds `data/processed/mna.duckdb` from scratch — the
pipeline is fully idempotent.

## 9. Testing

```bash
pytest tests/ -v
```
Covers: EV calculation, ratio edge cases (zero/negative EBITDA, zero
revenue, loss-making P/E), percentile math, comp-similarity ranking
(including a row with a missing feature), and valuation blending (including
the empty-input case).

## 10. API Reference

| Endpoint | Description |
|---|---|
| `GET /api/health` | Liveness check (also confirms the DB connection is alive) |
| `GET /api/companies` | List all companies with financials |
| `GET /api/companies/{id}` | Single company profile |
| `GET /api/companies/{id}/metrics` | Deterministic ratios & EV |
| `GET /api/comps/{id}?top_n=5` | Ranked comparable companies |
| `GET /api/transactions` | All precedent transactions |
| `GET /api/transactions/summary` | Multiple summary stats (mean/median/percentiles) |
| `GET /api/valuation/{id}?top_n_peers=5` | Full blended valuation |
| `GET /api/ai/comps/{id}` | One-shot AI explanation of the comp set (optional, needs Ollama) |
| `GET /api/ai/valuation/{id}` | One-shot AI explanation of the valuation (optional, needs Ollama) |
| `POST /api/ai/chat` | Interactive chat about the selected company (optional, needs Ollama) |

**Backend architecture note:** the API opens one shared read-only DuckDB
connection at startup and hands out cheap `.cursor()`s per request, instead
of opening a new file connection on every call — this is both more
efficient and avoids file-handle contention under concurrent requests (the
earlier per-request-connection pattern was the source of intermittent
failures under load). A global exception handler also ensures any
unexpected error returns a clean JSON 500 with a real message, rather than
the browser seeing a dropped connection.

## 11. Optional AI Analyst (Ollama)

The AI Analyst tab is a chat interface grounded in this app's own computed
numbers — it explains and answers follow-up questions, but the underlying
calculation layer (`src/analytics`, `src/ml`, `src/valuation`) is
completely separate and untouched by the model.

**Setup:**
```bash
# Install Ollama: https://ollama.com
ollama serve                    # in its own terminal
ollama pull llama3.2:3b         # default model — fast, ~2GB, CPU-friendly
```

**Model choice** (set via the `OLLAMA_MODEL` env var before starting the backend):

| Model | Size | Notes |
|---|---|---|
| `llama3.2:3b` (default) | ~2GB | Fastest, runs fine on a CPU-only laptop |
| `qwen2.5:7b-instruct` | ~5-6GB | Noticeably better financial reasoning; recommended if your hardware allows |
| `phi3.5` | ~2.5GB | Middle ground on size/quality |

```bash
export OLLAMA_MODEL=qwen2.5:7b-instruct   # optional upgrade
ollama pull qwen2.5:7b-instruct
uvicorn backend.main:app --reload --port 8000
```

If Ollama isn't running, the AI Analyst tab shows a clear error with a
Retry button — every other tab works completely independently of this
feature.

**If responses feel slow or vague**, this is almost always one of two
things, both already tuned for by default:

1. **Cold-start reload.** Ollama unloads a model from memory after 5
   minutes idle by default; reloading a 3-8B model costs 10-30+ seconds,
   which reads as "replying very late." This app sets `keep_alive=30m` on
   every request so the model stays warm through a normal working session
   — override with `export OLLAMA_KEEP_ALIVE=1h` (or any Ollama duration
   string) if you want it to persist longer.
2. **Unbounded, high-temperature generation.** An uncapped response at
   default temperature tends to ramble in generic language to fill space.
   The backend caps `num_predict` (~220-320 tokens) and lowers temperature
   to 0.3 so answers stay concrete and reference actual numbers instead of
   hedging. These are set in `src/ai/explain.py` (`GEN_OPTIONS` /
   `CHAT_OPTIONS`) if you want to tune further.

The chat tab also **streams** the reply token-by-token
(`POST /api/ai/chat/stream`) rather than waiting for the full answer, so
you see text appear within a second or two even when total generation
takes longer — this is what actually fixes the *felt* latency, independent
of raw model speed.
